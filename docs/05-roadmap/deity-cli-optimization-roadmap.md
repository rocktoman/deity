> 来源：2026-11-15 对 deity 1.0.0 的通读结论与 CLI 详细分析。
> 状态：**已立项（2026-11-15）**，本文为 V1.1 的立项依据，存放于 `docs/05-roadmap/`。
> 前置条件已解除：GitHub 仓库访问已于 2026-11-15 验证通过（连接器可读 deity 及私有仓库）。
> 开发分支：`feat/v1.1-m1-qwen-init` 起步，按下方里程碑逐批交付，每批以全量测试结果为准入。

## 现状（实测，2026-11-09 版，V1.0.0）

- 定位：*The model thinks. Deity executes, controls, and verifies.* 自研 Agent Loop，不用 LangChain/LangGraph，Python 3.12+，本地 CLI 优先。
- 规模：源码约 16,212 行（209 个 .py 文件），测试约 13,201 行 / 103 个测试文件，文档 55 篇，评估用例约 80 个；64 个提交集中在 2026-10-31 → 11-09。
- 仓库自述测试：584 通过 / 0 失败 / 16 跳过（HEAD），ruff + mypy strict 全过，10 分钟 soak 无内存增长。**注意：未在 Muse VM 复跑（无 pytest/uv），数字是仓库文档自述。**
- 已知短板：版本号 1.0.0 但**未发布 PyPI**，README 里的 `pipx install deity` 目前装不到；README 头部仍写“V0.3 已形成候选”，会低估项目；真实模型验证很薄（L3 只跑过 DeepSeek V4 Flash 的 E01–E03；真实 Docker、Windows CI、PyPI 发布均为 NOT_RUN）；本地模式不是沙箱（不开 Docker 时 shell 以用户权限在宿主机跑，只靠路径+审批拦）。

## 诊断：CLI 为什么“拉胯”

核心判断：**后端按 1.0 的标准在打磨，CLI 按 0.3 的标准在交差。CLI 不是 Harness 的附属品——对用户来说，CLI 就是产品本身。**

1. **CLI 是“事件打印器”，不是“工作台”。** `chat_render.py` 放弃 Rich Live 原地刷新，改行式增量输出；模型文本以纯文本裸奔（`markup=False`，Markdown、代码块都不渲染）；工具调用只有“▸ 开始 / ✓ 完成”两行，无折叠、无展开、无思考状态、无进度感。
2. **有两个前端，两个都是半成品。** CLI 行式打印；Textual TUI 的 `app.py` 只有 5 个 Static 文本块，**连输入框都没有**，只能“观看”已启动的 Run，按 a/d/c/r 批/拒/取消，本质是监视器，不是能对话的产品。
3. **一批命令是“占位命令”。** `/compact` 自认“没有独立的触发入口”，只能查看状态；`/cost` 经常只能告诉用户“token 未接通”。功能清单看着齐全，点下去是空的——这种落差比没有这个命令更伤信任。
4. **强项全藏在后端，用户感知不到。** 最值钱的是验证、回放、证据链、崩溃恢复，但 CLI 里它们只是数据库里的记录。用户能感知的只有“慢、素、没反馈”。护城河是可验证，但界面把它渲染成了不可见。

## V1.1 体验补课（先止血）

按顺序做，别平行铺开。验收标准：**录一段 3 分钟真实任务视频，和 Codex 并排看不寒酸。**

### 架构（不动 Core）

- **统一事件通道，废掉双轨制。** 现在 CLI 直播走 `RunService.run_stream()`，TUI/ClientService 走 SQLite 每 0.1 秒轮询——两套事件路径、两套语义。收敛成一条进程内事件总线（async queue / pub-sub），SQLite 只做持久化和事后回放，直播永远不走轮询。这是流式体验、取消时序、审批竞态等一切别扭的总源头。
- **拆掉 RunService 这个 1,298 行的上帝类。** 它同时管组装、授权、MCP、Skills、沙箱、委派、验证。按能力拆成可独立注入的服务（RunExecutor / ToolPipeline / ExtensionHost / VerificationHook），CLI 只依赖一个瘦的 `ChatService` 门面。
- **把“渲染状态”从事件流里分离，做真正的 ViewModel。** 现在 renderer 边收事件边 print，状态和输出焊死，做不了折叠、重绘、展开历史。改成：事件先折叠成一棵可变状态树（轮次 → 工具节点 → 结果），渲染器只负责把树画出来；CLI 行式、TUI 全屏、未来的 Web 共用这一棵树。V0.8 的 `RunViewModel` 只做了一半，需要做完。
- **配置系统推倒重做交互层。** `config.py` 786 行手写 TOML 校验，写错一个字段直接拒绝启动，用户还要自己手写 config.toml、自己设环境变量存 key。加 `deity init` 向导（选厂商 → 贴 key → 自动测通 → 生成配置）、`deity model add`、配置分层展示（`deity config show` 标明每项来自哪层）。入门 5 分钟能不能跑起来第一句话，决定这个项目有没有用户。

### 交互（投入产出比最高）

- **真流式渲染**：Markdown 渲染（代码块语法高亮）；工具节点可展开/折叠（默认只显示一行摘要，点开看参数和输出）；运行中常驻状态条：当前轮次 / 正在跑的工具+已耗时 / 上下文占用百分比 / 已花 token；长时间无输出时明确显示“模型思考中 / 工具运行中”，而不是光标干等。
- **二选一，别贪**：要么把 TUI 做成真产品（输入框+对话区+侧边文件/证据栏），CLI 退化为脚本模式；要么砍掉 TUI，把全部精力压到行式 CLI 的打磨上。以单人产能，建议**砍 TUI**，它现在是纯负债。
- **审批体验升级**：现在是“打印 Panel + 输数字”。做到：diff 默认只显示摘要（+12/-3），可展开全文；**会话级允许细化到命令模式**（如允许 `pytest *` 而不是允许整个 shell 工具）——现在的（工具名，工作区）粒度太粗，“本会话允许 shell”等于裸奔，与安全至上的定位自相矛盾。
- **输入补全做实**：`@文件` 现在是把全文塞进 prompt，既费 token 又原始；`/` 命令补全只有命令名，没有参数提示和模糊搜索。对齐主流即可，别自研选择器。


## V1.1 里程碑拆分（逐批交付，每批独立验收）

- **M1 配置与厂商（本批）**：`deity init` 生成最小可用配置（默认 Qwen / `qwen3.8-omni-flash`，
  只写 `api_key_env` 环境变量名，不写密钥值；拒绝默认覆盖已有配置）；Qwen 成为一等厂商
  （`provider = "qwen"`，默认端点 `https://dashscope.aliyuncs.com/compatible-mode/v1`，
  可用 `base_url` 覆盖）。验收：新增配置/组装/CLI 测试通过，全量测试不回退，
  并用真实 Qwen 模型完成一次端到端冒烟。
- **M2 事件与状态**：统一进程内事件总线（废除 CLI 直播与 ClientService SQLite 轮询双轨），
  事件先折叠成 ViewModel 状态树，渲染器只画树；RunService 按能力拆分的第一步
  （先抽 ToolPipeline，不动 Core 协议）。
- **M3 渲染与状态条**：Markdown 渲染、工具节点折叠/展开、常驻状态条
  （轮次/当前工具+耗时/上下文占用/token）、无输出时的思考/运行指示。
- **M4 审批与收尾**：会话级允许细化到命令模式（如 `pytest *`）；TUI 冻结决策落地
  （只保留监视用途并在文档标注，或移除默认入口）；`deity config show` 分层展示。

## V1.2 能力补课

验收标准：拿 10 个真实中型仓库任务跑自带 benchmark，和 V1.0 比成功率与平均轮次。

1. **工具升级**：全仓只有 10 个工具；`apply_patch` 是精确字符串替换（old 必须一字不差），模型稍有偏差就失败；没有多文件 patch、没有按行编辑；OpenAI 适配器写死 `parallel_tool_calls=False`，所有工具串行。优先补：统一 diff/patch 协议（支持多 hunk、模糊匹配）、只读工具并行执行、后台 shell（跑 dev server、长测试；现在 30 秒超时 + 16K 输出上限根本干不了）。
2. **代码理解**：代码智能 `lexical-v1` 是正则扫定义，没有 AST、没有 tree-sitter、没有 LSP、没有仓库地图。V1.x 最值得砸的一块：tree-sitter 增量索引 + 符号图 + 自动生成 repo map 注入上下文。
3. **上下文**：交互模式只带最近 4 轮问答；压缩有实现但没入口、策略也只是截断+快照。做分层上下文（系统提示/仓库地图/工作记忆/历史摘要）、工具结果自动摘要回注、上下文占用可视化+手动压缩真能触发；系统提示词现在写死在代码里的一段中文，进阶用户改不了——做成可分层覆盖的文件。
4. **模型层**：只支持两个厂商协议；`/model` 只能换同厂商的模型名，换不了厂商；没有失败自动切换、没有按任务路由（便宜模型做探索、强模型做修改）、没有 reasoning 强度控制、没有图片输入。模型无关是 slogan 里的卖点，实现只做到了“两个插口”。
5. **会话与可恢复**：SQLite 里有 checkpoint、事件、回放，地基全行业少见的扎实，但 CLI 层完全没兑现：没有 `/undo`（一键撤销本轮所有文件改动）、没有会话分支、不能编辑上一条提问重跑、resume 要用户记 run-id。建议每轮 Run 开始前自动做工作区快照（git stash 式或文件级），`/undo` 和 `/rewind` 直接回滚文件+上下文到任意轮次；会话列表带自动标题和全文搜索。

## V2.0 差异化：做 Claude Code 做不了的

验收标准：README 第一屏换成证据时间线的截图，而不是功能清单。

1. **证据时间线**：每轮结束不是一句“已完成”，而是一条可展开的证据链：改了什么（diff）、跑了什么验证（命令+结果）、哪一步是模型声称但未验证的（标黄）。把 Verification 从后台服务变成 CLI 的主视觉。
2. **回放做成产品功能**：只读 replay 和回归门禁是别人没有的。做成 `/replay <run-id>` 在终端里重演一次历史运行、`/eval` 随手把当前任务沉淀成评估用例——面向团队用户，这是“可审计的 Agent”，是能卖钱的定位。
3. **信任分级自动化**：基于评估数据给任务自动定级——低风险（只读/有测试覆盖）自动执行，高风险（删文件/改配置）才打断审批。把“审批疲劳”用自己的验证能力解决，而不是靠用户勾选“全部允许”。
4. **可写多 Agent 委派**：现在委派只读，子 Agent 结果靠截断到 16K 字符拼回去。补上“可写委派 + 结果以 patch 形式回收 + 父级审查”最后一公里（已有 worktree 实验和委派树基础）；模型路由/失败切换与 `deity stats`（本周成功率、回滚率、各模型成本/效果对比——已有 benchmark 和 A/B 实验框架，缺一个面向用户的出口）同属这一层。

## 工作方式提醒（来自复盘）

- 不要再按“版本号功能清单”开发：V0.1→V1.0 每版堆一个大功能、每版写验收文档的模式，产出的是文档齐全的半成品矩阵。改成以“一个真实用户从安装到完成任务的全程录像”为每版验收。
- CLI 就是产品本身。Core 再强，界面拉胯等于产品拉胯，这个认知不扭转，优化清单列得再细也没用。
