### 0.2 已有能力（可复用，不重造）

- **事件持久化**：`events` 表已有 `(run_id, sequence)` 唯一约束与 `idx_events_run_seq` 索引，`SQLiteSessionRepository.events(run_id)` 可按序读事件；`tool_executions` 有 `call_id` 唯一约束与审批字段；`run_leases`、`checkpoints`、`run_lineage` 已存在。缺：事件无 `schema_version`、无快照表、无订阅/重放 API。
- **审批**：`RunService` 接受同步回调 `approve(name, args) -> bool`，CLI 用 `typer.confirm` 打印工具参数（`main.py:175`、`plan.py:170`）；Plan 审批有 `approve_plan_and_create_build` 与状态机。缺：异步/可等待的审批请求对象、审批去重、TUI 审批弹窗。
- **运行服务**：`RunService.from_config()` 已组装模型/工具/MCP/Skills/Hooks/Plan/沙箱/多 Agent；`cancel(run_id)`、`resume(run_id)`、`inspect(run_id)` 已有。缺：统一客户端协议（`start_run/subscribe_events/approve/cancel/resume`）——没有一个 CLI/TUI 共用的、有类型契约的入口。
- **配置**：`application/config.py` 的 `load_config()` 只读单一 TOML（默认 `~/.config/deity/config.toml`），校验严格、错误不泄露密钥；已有 `[run]` `[permission]` `[model]` `[extensions]` `[mcp]` `[coding]` `[code_intelligence]` `[git_guard]` `[verification]` `[sandbox]` `[multi_agent]`。缺：配置优先级（CLI > project > user > default）、`[tui]`/`[eval]` 配置段、`deity doctor`。
- **评估**：`evals/runners/` 已有 7 个运行器，都是 `run_case()`（跑 pytest selector、写 `evals/reports/<id>.json/.md`）的薄包装：`runner.py`（E01–E08）、`reliability.py`（R01–R06）、`extensions.py`（X01–X06）、`advanced.py`（A01–A12）、`sandbox.py`（S01–S12）、`multi_agent.py`（M01–M12）、`l3_candidate.py`（真实模型，需密钥）。`evals/cases/` 共 56 个 YAML（E8+R6+X6+A12+S12+M12），每个只含 `id` + `pytest` selector。`tests/fixtures/` 有 `python-mini-repo`、`java-mini-repo`、`typescript-mini-repo` 三个迷你仓库。缺：数据集清单/版本化、环境 hash、评分（除 pass/fail 外无指标）、A/B 实验、回放/回归门禁。`evals/reports/` 当前不存在（运行器运行时生成）。
- **CI**：`.github/workflows/ci.yml` 已有 ubuntu+macos × py3.12/3.13 矩阵，跑 ruff/mypy/pytest + 6 个确定性 eval 运行器，另有 `sandbox-docker` job（真实 Docker）。缺：Windows、SBOM、漏洞扫描、发布流水线。
- **版本**：`pyproject.toml` 与 `src/deity/__init__.py` 的 `__version__` 都是 `0.1.0`，未随 V0.3–V0.7  bump；这是 v1.0 要修的。

- v0.9：数据集与隔离（固定 commit/任务/断言/环境 hash）、运行器评分指标、A/B 实验、只读回放。

### 0.4 设计文档的去模板化说明

三份设计文档（`docs/05-roadmap/deity-v0.8/0.9/1.0-design.md`）第 2 节各模块的“建议实现步骤”五条是逐模块重复的模板文字，本计划不照抄；每版按“契约 → Fake/确定性测试 → 实现 → CLI/TUI 入口 → 评估证据”的真实顺序写具体文件。验收标准照抄设计文档第 5 节（见各版 §验收标准）。

## 1. 总体原则

1. 边界不变：`interfaces → application → core ports ← adapters`；Core 不导入 Typer/Rich/厂商 SDK/SQLite/FastAPI/MCP SDK/Docker SDK；新能力经 Protocol 注入。
2. 先补失败测试再实现；每版新功能同步交付确定性单测 + 集成测试 + eval fixture + 事件证据。
3. 新能力默认关闭（配置开关），关闭后旧流程可运行；数据库/事件/配置格式带版本，可前向迁移、旧事件只读兼容；破坏性改动先写 ADR。
4. 质量门禁每版必跑：`ruff check .`、`ruff format --check .`、`mypy src`、`pytest -q`，加该版 eval 运行器；未跑的标 NOT_RUN，绝不伪称通过。
5. commit message 用中文；不在日志/测试快照中输出密钥；不自动运行破坏性 Git 命令，不覆盖用户未提交修改；动手前先 `git status`。
6. 依赖最小引入：Textual 仅 v0.8 可选 extra；统计只用标准库 `statistics`（v0.9 不引入 scipy/numpy）；构建/扫描工具仅 v1.0 在 CI 用，不进运行时依赖。

## 2. V0.8 — Developer Experience / TUI

### 2.1 目标

在不改变核心协议的前提下提供可用 TUI 与更顺畅的交互；CLI 与 TUI 共用同一服务层、同一 Run 呈现同一状态与证据。

### 2.2 S1 — 统一客户端协议

**新建文件**

- `src/deity/core/contracts/client.py`：`ClientEvent`（`seq: int`、`run_id: str`、`schema_version: int = 1`、`kind: str`、`payload: dict`、`created_at: str`）、`RunHandle`（`run_id`、`session_id`、`status`）、`EventSubscription`（`subscribe()` 异步迭代器 + `close()`）、`ApprovalRequest`（`approval_id`、`run_id`、`call_id`、`tool_name`、`args` 摘要（不含文件内容全文）、`status: pending/approved/denied`、`decided_at`）、`ClientError` 错误码（`run_not_found` / `already_decided` / `subscription_closed`）。
- `src/deity/application/client_service.py`：`ClientService`，包装一个 `RunService`，提供 `start_run(task, model_name, session_id) -> RunHandle`、`subscribe_events(run_id, after_seq=0) -> EventSubscription`（快照：先读 SQLite 已持久化事件，再跟随新事件；断线重连用 `after_seq` 续订，不重复执行工具）、`approve(approval_id, decision) -> ApprovalRequest`（同一 `approval_id` 重复决定返回首次结果，不重复提交）、`cancel(run_id)`、`resume(run_id)`。审批等待用 `asyncio.Event`，不忙轮询；慢消费者用有界队列（满则断开订阅并报错，不丢事件后静默续跑）。
- `src/deity/adapters/events.py`：`SQLiteEventSubscriber`，读 `SQLiteSessionRepository.events()` 做快照 + 轮询新事件（间隔可配，默认 100ms，上限 1s 退避）；只读，不写事件。

**修改文件**

- `src/deity/core/contracts/__init__.py`：导出上述类型。
- `src/deity/application/run_service.py`：把审批回调从同步 `approve` 扩展为可等待的审批端口：`RunService` 内部持有一个 `ApprovalPort`（Protocol，`request_approval(...) -> ApprovalRequest`），默认实现仍走同步回调（CLI 兼容），`ClientService` 注入异步实现；`run()` 接受可选的 `event_sink: EventPublisher`，把模型/工具/状态事件经 `publish()` 落库（已有 `events` 表，`sequence` 由仓储分配）。

**测试（先写失败测试）**

- `tests/unit/test_client_protocol.py`：事件 seq 单调、快照+增量不丢不重、重连 `after_seq` 续订、慢消费者断开、乱序事件不应用、重复审批只生效一次、审批拒绝产生终态/等待态、取消传播。
- `tests/integration/test_client_service.py`：用 FakeModel 跑完整 `start_run → subscribe → approve → 完成` 闭环；CLI 与 ClientService 对同一 Run 读到同一状态与证据。

**验收**：同一 Run 在 CLI/TUI 呈现一致状态与证据；事件重连不丢失/重复执行工具。

### 2.8 V0.8 风险与回退

- Textual 版本漂移：锁定版本区间并记入 `uv.lock`；回退为关闭 `[tui].enabled`，CLI 不受影响。
- 事件轮询延迟：默认 100ms，上限退避 1s；慢消费者断开订阅是预期行为，Run 本身不受影响。
- 审批竞态：以 `approval_id` + SQLite 唯一约束为准，重复决定返回首次结果。

## 3. V0.9 — 评估与实验平台

> 依赖：v0.8 的 `ClientService` 事件订阅（回放读事件）与 `DoctorReport` 环境检查（评估报告的环境部分）。

### 3.1 目标

把 V0.1 起已存在的测试体系升级为可重复、可比较、可追溯的评估平台；不引入 LLM-as-judge 判定代码正确。

### 3.2 S1 — 数据集与隔离

**新建文件**

- `src/deity/core/contracts/eval.py`：`EvalCase`（`id`、`title`、`language: python|java|typescript`、`repo_fixture`、`task`、`test_command: tuple[str, ...]`、`policy`、`budget_seconds`、`expected_changes`、`assertions`、`dataset_version: str`）、`FixtureManifest`（`name`、`language`、`source_path`、`sha256`、`environment_hash`）、`EvalEnvironment`（`python`、`os`、`deity_version`、`config_hash`、`git_commit`）、`DatasetVersion`（`version: str`、`cases: tuple[str, ...]`）。
- `src/deity/application/eval_service.py`：`EvalService`：加载 `evals/datasets/v1/*.yaml`，校验 schema；运行前把 fixture 复制到隔离临时目录（`tempfile.mkdtemp`，不用 worktree 写原仓库；跑完清理，失败时保留路径写进报告）；记录环境 hash（Python 版本 + `git rev-parse HEAD` + 配置 hash，不含密钥）。
- `evals/datasets/v1/manifest.yaml`：数据集版本 `v1`，至少 20 个固定 case 的清单。

**新建 fixture case（至少 20 个，覆盖 Java/Python/TS）**

- 复用现有 3 个迷你仓库 + 新增确定性任务：在 `evals/datasets/v1/` 新建 `B01–B20.yaml`，每案固定 `repo_fixture`（`python-mini-repo` / `java-mini-repo` / `typescript-mini-repo`）、任务说明、可执行断言（pytest selector 或固定 shell 命令，超时 60s）。分布：Python 8、Java 6、TypeScript 6。任务类型：读分析、加函数、修 bug、符号定位、补丁边界、脏文件保护、非 Git 工作区、验证通过/失败。**不**复用 E/A/M/S 的 selector 当 B 案断言时要写明映射关系，避免同一断言挂两个 ID。
- 隔离：每个 B 案跑在独立复制目录；禁止 case 间共享 `deity.db`（每案独立临时 DB）。

**测试**：`tests/unit/test_eval_dataset.py`（manifest 校验、缺 fixture 报错、环境 hash 稳定、数据泄漏：case 不能读到其他 case 的临时目录）、`tests/integration/test_eval_isolation.py`（两案并行/先后跑，互不污染）。

### 3.3 S2 — 运行器与评分

**新建文件**

- `src/deity/core/contracts/eval.py`（续）：`EvalRunner`、`Scorer`、`MetricRecord`（`case_id`、`passed`、`duration_ms`、`tool_calls`、`turns`、`input_tokens`、`output_tokens`、`failure_category`）、`EvidenceBundle`（`report_json`、`report_md`、`events` 摘要）。
- `evals/runners/benchmark.py`：`python -m evals.runners.benchmark [--dataset v1] [--only B01...]`，确定性离线（FakeModel）跑 B01–B20，输出 `evals/reports/B*.json/.md` 与汇总 `evals/reports/benchmark-v1.json`（含环境、模型 `deterministic-pytest`、配置 hash、代码版本 `git rev-parse HEAD`、每案指标）；评分只用可执行断言（测试通过/任务成功/安全违规/成本/耗时/轮次），**不用模型自评**。
- `evals/runners/runner.py` 等既有运行器不动（E/R/X/A/S/M 各守其案）。

**测试**：`tests/unit/test_eval_scorer.py`（指标聚合、失败分类、空结果不 crash）、`tests/e2e/test_benchmark_runner.py`（跑 2 个 B 案端到端，报告字段齐全）。

### 3.4 S3 — A/B 实验

**新建文件**

- `src/deity/core/contracts/eval.py`（续）：`ExperimentConfig`（`name`、`dataset_version`、`repetitions: int >= 2`、`variants: tuple[VariantConfig, ...]`）、`VariantConfig`（`name`、`harness_patch: dict`——只允许改一项受控变量，如 `compaction_enabled` 或 `max_turns`，多于一项校验失败）、`ComparisonReport`（每变体均值/中位数/p95/失败类别，禁止选择性汇报：所有变体、所有 case 都列出）。
- `evals/runners/experiment.py`：`python -m evals.runners.experiment --config evals/experiments/<name>.yaml`，固定模型/prompt/温度/任务集/预算/环境，只改变一项 Harness 策略；每任务重复 `repetitions` 次（默认 3）；统计用标准库 `statistics`（均值/中位数/分位数，无 scipy/numpy）；输出 `evals/reports/exp-<name>.json/.md`。
- `evals/experiments/compaction-ab.yaml`（示例实验）：对照 `compaction_enabled=false` vs `true`，其余全固定。

**测试**：`tests/unit/test_experiment.py`（多变量校验失败、重复次数不足报错、报告含全部变体与全部 case、统计计算正确）。

### 3.5 S4 — 回放与回归

**新建文件**

- `src/deity/application/replay.py`：`TraceReplayer`：读 `evals/reports/<id>.json` 或 SQLite `events`，只读重放：重建 `RunViewModel`/终态与证据摘要；**绝不执行真实写入或网络副作用**（重放时工具分发器替换为 `ReplayDispatcher`，任何写工具调用直接拒绝并记为 `replay_blocked`）；事件 `schema_version` 不一致时只读旧事件并标注 `schema_mismatch`，不迁移写入。
- `src/deity/application/regression_gate.py`：`RegressionGate.check(reports_dir)`：PR 门禁——关键安全/协议门禁（`tests/unit/test_client_protocol.py`、`tests/integration/test_tool_workflow.py` 等白名单）任一失败即 gate 失败；输出 `evals/reports/regression-gate.json`。
- CLI：`deity eval replay <report-or-run-id>`、`deity eval gate`（在 `main.py` 加 `eval` 子命令组，不另起入口）。

**测试**

- `tests/unit/test_replay.py`：回放不写文件（用临时工作区断言无变化）、不发网络、写工具被拒、旧 schema 事件只读。
- `tests/integration/test_replay_cli.py`：`deity eval replay` 对真实报告输出同一终态；`deity eval gate` 在人为破坏一案时失败。

### 3.7 V0.9 验收标准（照抄设计文档第 5 节）

- [ ] 至少 20 个固定 fixture 案例，覆盖 Java/Python/TS

### 3.8 V0.9 风险与回退

## 5. 交付顺序与 commit 规划

1. 基线 + 本计划文档 → commit「编写 v0.8-v1.0 实施计划」。
2. v0.8：S1 → S2 → S3 → S4，每迭代一个 commit（中文 message），每版结束跑门禁并写验收记录 → commit「实现 V0.8 …」「V0.8 验收记录」。
3. v0.9：S1 → S2 → S3 → S4，同上。
4. v1.0：S1 → S2 → S3 → S4，同上；最后跑全量门禁。
5. 全量完成后向用户汇报，确认后 push 到 `origin main`（用户在 Mac 上 pull）。**不要提前 push。**
6. v0.8–v1.0 测试全部跑通后，再按 `docs/03-development/cli-chat-refactor-plan.md`（用户已确认，Phase 0–4）实施 CLI 聊天重构；Phase 0 先确认 v0.8 的 `subscribe_events` 是否已落地，已落地则复用、不另起一套。每阶段测试跑通，失败就分析原因、改代码、再跑。
7. 最后做总体汇总（v0.8–v1.0 + CLI 重构）：每版改了哪些文件、每轮测试结果、修掉的失败及其根本原因、还剩什么 NOT_RUN（只限真实模型 L3 需密钥那种，写明原因）、遗留风险；汇总完成后 push 到 `origin main`，汇报里写明 push 结果。
