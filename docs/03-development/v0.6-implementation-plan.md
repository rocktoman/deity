# Deity V0.6 Execution Sandbox 实施计划

> 状态：规划完成，尚未实施。需求依据：[V0.6 设计](../05-roadmap/deity-v0.6-design.md)。实施基线为 V0.5 本地候选、SQLite v4、E/R/X/A 确定性评估；本文中的接口、命令和表结构必须在编码前由 ADR-012 最终冻结。

## 1. 目标、范围与完成定义

V0.6 为高风险命令和确定性验证增加可选执行后端。启用 Docker 后端时，Deity 在复制出的 staging 工作区中运行命令，默认禁网、非 root、只读根文件系统、限制 CPU/内存/PID，不继承宿主环境秘密；执行结果、清理结果和工件清单先持久化，再按现有权限与 Git Guard 规则决定是否把文本变更回传到用户工作区。

本版本交付五项能力：

1. 与 Docker 无关的 `ExecutionBackend` 契约、能力协商、生命周期和 Fake/Local 后端。
2. 基于受控 Docker CLI argv 的 `DockerExecutionBackend`，以及 `deity sandbox doctor/run`。
3. 复制式 staging 工作区、边界复核、差异清单、两阶段工件回传和确定性清理。
4. 高风险 `shell` 与 Verification 对统一执行端口的接入；Git、rg、Code Intelligence 等宿主只读辅助命令暂不迁移。
5. SQLite v5 审计事实、S01–S12 评估、Linux Docker 集成门禁、使用/回退文档和候选报告。

V0.6 完成必须同时具备：接口与配置契约、正常/拒绝/异常/超时/取消/崩溃测试、真实 Docker fixture、资源与秘密回归、SQLite 迁移/恢复演练、CLI 演示、S01–S12、旧 E/R/X/A 全量回归、文档与可执行回退。任何未执行项目必须写 `NOT_RUN`，Docker 可用不等于容器绝对安全。

### 1.1 明确不做

- 不引入 LangChain、LangGraph、Deep Agents Runtime、FastAPI、TUI、MCP 新能力、Multi-Agent、RAG 或自动模型切换。
- 不提供 Kubernetes、远程 Docker daemon、SSH Docker context、Podman、containerd 或多租户服务端执行。
- 不宣称容器能防御内核漏洞、恶意 Docker daemon、宿主已泄漏秘密或所有容器逃逸。
- 不把宿主工作区直接以可写 bind mount 挂入容器；V0.6 主路径固定为 staging copy。
- 不自动拉取 tag-only 镜像，不在一次 Run 中自动 build/pull 镜像，不挂载 Docker socket，不启用 privileged，不添加 Linux capability。
- 不实现域名级网络防火墙。首版只支持 `none`，或显式允许的预创建 Docker network 名称；后者不宣称是域名 allowlist。
- 不容器化模型 SDK、MCP、Skills、Hooks、Git/rg/索引缓存，也不一次性重写所有 `subprocess` 调用。
- 不把容器产生的二进制、设备、socket、symlink、超大文件或未知编码自动写回用户工作区。
- 不自动 commit、stash、reset、clean，也不因容器失败自动重放未知副作用。
- Windows 在 V0.6 只返回明确的 `unsupported_platform`/doctor 诊断；不得静默回退 Local。macOS Docker Desktop 可手工验证，但不以 GitHub macOS runner 上存在 Docker 为前提。

## 2. 当前基线与缺口

当前 V0.5 已有：

- `RunService` 负责组合 `LocalToolDispatcher`、Plan policy、Code Intelligence、Git Guard、Skills/MCP/Hooks。
- `LocalToolDispatcher` 负责 shell 的 schema、审批、宿主进程、超时、输出上限和进程组取消。
- `VerificationExecutor` 另有一套宿主进程实现，并把退出码转换为四状态 Evidence。
- `WorkspaceSnapshot`、`ChangeSet`、`FileChange`、SafePatch、dirty allowlist 和 read-before-write 可保护用户原改动。
- SQLite v4 已持久化计划、快照、变更集与验证事实；V0.5 本地基线为 255 tests、E 8/8、R 6/6、X 6/6、A 12/12。远程 CI 和真实模型 L3 的历史记录仍为 `NOT_RUN`，不能当作 V0.6 当前通过证据。

主要缺口：

1. Core 没有进程执行端口；shell 与 Verification 重复实现 subprocess 生命周期。
2. `RunService` 和 `VerificationService` 直接构造具体本地执行器，无法按能力安全选择后端。
3. 当前 shell 直接在用户工作区执行，资源限制只有 timeout/输出上限，没有 CPU/memory/PID/network/rootfs 隔离。
4. 没有 staging manifest、容器身份、镜像 digest、cleanup outcome 或孤儿容器协调事实。
5. 当前 CI 没有 Fake sandbox 门禁和 Linux Docker 专用门禁。

实施原则是增量替换：不改 AgentLoop 的模型/工具协议，不改现有工具名，不让 Docker adapter 访问 SQLite 或作业务授权。`shell` 和 Verification 先接入统一端口；旧开关关闭时保持 V0.5 行为与请求指纹不变。

## 3. S0：ADR-012 必须冻结的决策

编码前新增 `docs/02-architecture/adr-012-v0.6-execution-sandbox.md`，至少冻结下列决策：

| 决策 | V0.6 选择 | 原因与边界 |
|---|---|---|
| 后端端口 | Core 定义 `ExecutionBackend`；Application/Core coordinator 驱动 `prepare → execute → collect → cleanup` | Adapter 只做 I/O，不授权、不写业务状态 |
| 接入范围 | 高风险 `shell` 与 Verification | 最小垂直切片；Git/rg 保持宿主只读路径 |
| Docker 接入 | 使用外部 Docker CLI，全部通过 `create_subprocess_exec(*argv)` | 不新增 Python 运行依赖；禁止 shell 字符串拼接 |
| 工作区 | 复制到 Deity 管理的临时 staging；容器仅挂 staging | 用户工作区不直接暴露为容器可写挂载 |
| 根文件系统 | `read-only`，只为 `/tmp`、`/run` 等必要路径提供有界 tmpfs | 降低镜像层写入和持久残留 |
| 身份 | 默认使用非 root 数字 UID/GID；doctor 执行写入探针 | 不假定镜像存在特定用户名 |
| 权限 | `schema → policy → boundary → approval → durable intent → backend → audit` | Docker 不能替代现有权限链 |
| 网络 | 默认 `none`；非 none 只接受配置 allowlist 中的预创建 network，且需显式审批 | 不宣称域名级隔离 |
| 镜像 | 运行只接受 digest 固定的配置；`--pull=never`；build/pull 不在普通 Run 内 | 防止 tag 漂移和隐式网络副作用 |
| 工件 | 先产生 `ArtifactManifest`，再经权限、Git Guard、preimage 和原子写逐项回传 | 容器不能直接绕过 V0.5 保护 |
| Verification | 使用同一 backend，但 Verification 状态仍由退出码和已提交 Evidence 聚合 | Adapter 不声明测试通过 |
| 不可用策略 | `required=true` 或显式 Docker 后端时 fail closed；不自动降级 Local | 防止高风险命令误落宿主 |
| 恢复 | 未知 execute/collect/apply outcome 不重放；重启后进入 manual review/cleanup reconciliation | 保持 V0.3 副作用不变量 |
| 存储 | SQLite v4→v5，迁移前生成并验证 `.v4.bak` | sandbox 生命周期需要可查询事实 |
| 兼容 | `[sandbox].enabled=false` 时不 doctor、不创建 staging、不改变旧工具/指纹 | 保持 V0.5 默认路径 |

### 3.1 依赖评审

V0.6 必选实现不新增 Python 运行依赖，外部前置为本机 Docker CLI 与可访问的本地 daemon。ADR 必须记录：

- Docker CLI/Engine 的实际兼容版本区间与验证平台；锁定的是 Deity 支持区间，不把最新版本写死在代码。
- Docker 组件许可证、维护状态、daemon 高权限风险、镜像供应链风险和升级策略。
- 替代方案：Docker SDK for Python、Podman/OCI CLI、自研低层 API；说明首版为何不选，以及未来替换端口。
- 移除成本：关闭开关后 Local backend 继续工作；删除 Docker adapter 不影响 Core/数据库旧事实读取。
- CI fixture 镜像只从仓库内 Dockerfile 构建并以本地 image ID/digest 运行，候选命令禁止隐式 pull。

如实现过程中发现 Docker CLI 无法可靠提供所需能力，必须暂停并修订 ADR，不得临时引入 SDK 或放宽安全默认值。

## 4. 目标架构与调用时序

```text
CLI sandbox/run/verify
  → RunService / SandboxService / VerificationService
    → ExecutionPolicy + BackendSelector + ExecutionCoordinator
      → ExecutionBackend Protocol
        ← LocalExecutionBackend
        ← FakeExecutionBackend (tests only)
        ← DockerExecutionBackend
      → ExecutionJournal Protocol ← SQLite v5
      → WorkspaceStager / ArtifactCollector / ArtifactApplier
        → Git Guard + ChangeSetRepository + Safe atomic write
```

固定时序：

```text
validate argv/spec
  → permission + backend capability decision
  → capture host baseline
  → persist SandboxExecutionPrepared (durable intent)
  → backend.prepare (staging + docker create)
  → backend.execute (docker start/attach or local process)
  → backend.collect (exit/logs/inspect + artifact manifest)
  → persist typed result and manifest
  → optional artifact review/apply via Git Guard
  → backend.cleanup (always in finally)
  → persist cleanup report
  → expose ToolResult / VerificationEvidence
```

规则：

- 工具的 `ToolClaimed` 仍先于 `dispatch`；sandbox intent 是该已批准工具内部的后端事实，不替代 `call_id` 唯一约束。
- `cleanup` 必须运行于 `finally`，但 cleanup 失败不能覆盖原始执行结果；两者分别持久化。
- 只有 result、manifest、所需 cleanup 事实持久化成功后，CLI 才能宣称执行完成。
- `execute` 后连接丢失或 daemon 状态不明时标 `unknown`，按 container ID/label 协调，不重新 create/start 同一操作。
- Local backend 只提供 `process_isolation=false`；策略要求容器能力时，selector 在 intent 前拒绝 Local。

## 5. Core 契约与不变量

新增 `src/deity/core/contracts/execution.py`，从 `core/contracts/__init__.py` 重导出。建议语义如下，字段名由 ADR/失败测试最终冻结：

```python
class BackendKind(StrEnum):
    LOCAL = "local"
    DOCKER = "docker"
    FAKE = "fake"

class ExecutionStatus(StrEnum):
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    DENIED = "denied"
    TIMED_OUT = "timed_out"
    CANCELLED = "cancelled"
    UNKNOWN = "unknown"

@dataclass(frozen=True)
class ResourceBudget:
    timeout_seconds: float
    cpu_count: float | None
    memory_bytes: int | None
    pids_limit: int | None
    output_chars: int
    tmpfs_bytes: int | None

@dataclass(frozen=True)
class BackendCapabilities:
    kind: BackendKind
    process_isolation: bool
    read_only_rootfs: bool
    network_none: bool
    named_network: bool
    cpu_limit: bool
    memory_limit: bool
    pids_limit: bool
    copy_workspace: bool
    platform: str
    available: bool
    diagnostics: tuple[str, ...] = ()

@dataclass(frozen=True)
class SandboxSpec:
    backend: BackendKind
    image: str | None
    workspace_mode: Literal["copy"]
    network: str
    env_names: tuple[str, ...]
    resource_budget: ResourceBudget
    read_only_rootfs: bool = True
    non_root: bool = True
    artifact_policy: Literal["discard", "review"] = "discard"

@dataclass(frozen=True)
class WorkspaceMountPolicy:
    mode: Literal["copy"]
    container_path: str
    exclude: tuple[str, ...]
    max_files: int
    max_bytes: int
    reject_symlinks: bool = True

@dataclass(frozen=True)
class ExecutionRequest:
    execution_id: str
    run_id: str
    call_id: str | None
    argv: tuple[str, ...]
    cwd: str
    spec: SandboxSpec

@dataclass(frozen=True)
class SandboxHandle:
    execution_id: str
    backend: BackendKind
    opaque_id: str
    staging_root: str | None

@dataclass(frozen=True)
class ExecutionResult:
    execution_id: str
    status: ExecutionStatus
    exit_code: int | None
    stdout: str
    stderr: str
    duration_ms: int
    truncated: bool
    backend_metadata: dict[str, str]
    error_code: str | None = None

@dataclass(frozen=True)
class ArtifactEntry:
    path: str
    operation: Literal["create", "modify", "delete"]
    before_sha256: str | None
    after_sha256: str | None
    size: int | None
    mode: int | None

@dataclass(frozen=True)
class ArtifactManifest:
    manifest_id: str
    execution_id: str
    entries: tuple[ArtifactEntry, ...]
    status: Literal["collected", "rejected", "applied", "partial", "unknown"]
    diagnostics: tuple[str, ...] = ()

@dataclass(frozen=True)
class SandboxCleanupReport:
    execution_id: str
    status: Literal["cleaned", "not_found", "failed", "unknown"]
    container_removed: bool
    staging_removed: bool
    diagnostics: tuple[str, ...] = ()

class ExecutionBackend(Protocol):
    async def capabilities(self) -> BackendCapabilities: ...
    async def prepare(self, request: ExecutionRequest) -> SandboxHandle: ...
    async def execute(self, handle: SandboxHandle, request: ExecutionRequest) -> ExecutionResult: ...
    async def collect(self, handle: SandboxHandle, result: ExecutionResult) -> ArtifactManifest: ...
    async def cleanup(self, handle: SandboxHandle) -> SandboxCleanupReport: ...
```

另定义 `ExecutionJournal`、`WorkspaceStager`、`ArtifactCollector`、`ArtifactApplier`、`BackendSelector` Protocol。`WorkspaceMountPolicy` 在 V0.6 只允许 copy，名称保留未来后端扩展语义，但不能借此开放直接可写宿主挂载。Core DTO 不出现 Docker SDK、SQLite row、Typer、`subprocess.Process` 或宿主绝对 home 路径。

### 5.1 运行时不变量

1. `execution_id` 全局唯一；同一 `(run_id, call_id)` 最多一个活动 sandbox execution。
2. 参数完整、Schema 有效、权限批准、能力匹配和 durable intent 完成前，不创建容器。
3. 要求 isolation/network/resource capability 时，缺少任一能力都拒绝；不以“尽力而为”继续。
4. Docker image 必须是配置允许的 digest 固定引用或 CI 本地 image ID；运行时 `pull=never`。
5. 容器不得接收 Docker socket、宿主 home、Deity 数据库、SSH agent 或未列名环境变量。
6. 容器只能看到 staging 工作区；staging 之外的路径不进入 artifact manifest。
7. Artifact 先收集后应用；未通过 symlink/special-file/size/path/preimage/dirty 检查的条目不得写回。
8. Verification 的 artifact policy 固定为 `discard`；测试生成物不能污染用户工作区。
9. timeout/cancel 必须停止 attach 客户端并强制清理容器；cleanup failure 单独报告并阻断候选通过。
10. unknown execute/apply outcome 不自动重放；恢复前先按持久化 container ID/label 协调。
11. Run 终态、Execution 状态、Verification 状态和 cleanup 状态彼此独立，不互相伪造。
12. 禁用 sandbox 时，不创建 staging、容器、v5 execution row，也不改变 V0.5 工具 definitions。

## 6. 配置、策略与恢复指纹

在 `application/config.py` 增加严格版本化配置，默认关闭：

```toml
[sandbox]
version = 1
enabled = false
backend = "local"          # local | docker
required = false
image = ""                 # docker 时必须为 digest 固定引用或本地 image ID
workspace_mode = "copy"    # V0.6 只接受 copy
artifact_policy = "discard" # discard | review
network = "none"
allowed_networks = []
env_names = []
read_only_rootfs = true
non_root = true
cpu_count = 1.0
memory_mb = 1024
pids_limit = 128
tmpfs_mb = 256
timeout_seconds = 300
cleanup_timeout_seconds = 15
max_output_chars = 16000
max_workspace_files = 50000
max_workspace_bytes = 1073741824
max_artifact_files = 200
max_artifact_bytes = 52428800
exclude = [".git", ".deity", ".env", ".env.*"]
```

最终上下限在失败测试和首轮基线后由 ADR 校准。至少校验：

- 未知字段/版本/枚举/布尔类型/数值越界全部 fail closed。
- `enabled=true, backend=docker` 时 image 非空且固定 digest；tag-only 拒绝。
- `required=true` 不允许 backend=local。
- 非 `none` 网络必须位于 `allowed_networks`，名称满足有界字符规则；仍需一次明确审批。
- `env_names` 只允许规范环境变量名，默认空；只审计名字，不持久化值。
- `read_only_rootfs` 和 `non_root` 在 V0.6 Docker required 模式必须为 true，不能通过项目配置关闭。
- exclude 只能是有界相对 pattern，不能用它突破 workspace root；默认排除项不能被项目配置移除，只能追加。
- `artifact_policy=review` 不等于授权写回，仍走 `permission.workspace_write`、Plan target 和 Git Guard。

`Config` 新增 `sandbox`，并提供不含秘密/绝对路径的 `sandbox_fingerprint()`。只有 `enabled=true` 时，backend、required、image digest、network、limits、env names、workspace/artifact policy 和 adapter schema version 才进入 `AgentRequest.policy_fingerprint`；禁用时保持旧 V0.5 指纹。

恢复时还要比较 backend kind、image digest、capability snapshot 和 staging/artifact 状态。配置改变、镜像漂移、存在活动/unknown execution 或 cleanup 未完成时，`runs inspect` 返回 `manual_review`，不得直接 resume。

## 7. Local/Fake/Docker 后端

### 7.1 LocalExecutionBackend

- 从 `LocalToolDispatcher._process` 和 `VerificationExecutor` 提取公共宿主进程逻辑到 `adapters/execution/local.py`。
- 保留 argv、cwd、env 白名单、start_new_session、timeout、输出上限、SIGTERM→宽限→SIGKILL 和取消传播。
- capabilities 明确 `process_isolation=false`、`network_none=false`、资源限制能力按实际平台声明；不能伪装成 sandbox。
- sandbox 关闭时使用 Local，确保旧 shell 与 Verification 语义、错误码和测试不变。

### 7.2 FakeExecutionBackend

- 位于 tests fixture 或 `adapters/execution/fake.py`（若生产包需要契约测试），支持脚本化成功、拒绝、prepare 失败、execute unknown、collect 失败、cleanup 失败、取消和重复调用。
- 记录严格调用顺序与次数，禁止测试只断言最终 CLI 文本。
- 单测和普通 CI 不依赖本机 Docker。

### 7.3 DockerExecutionBackend

`adapters/execution/docker.py` 只通过 argv 调用 Docker CLI。建议使用可审计生命周期：

1. doctor 检查 CLI、daemon、server OS/arch、当前 context、镜像是否本地存在、digest 是否匹配、关键 limit 能力和 staging 写探针。
2. `docker create` 生成稳定 container ID；名称与 labels 含版本、run_id hash、execution_id，禁止原始任务文本。
3. 创建参数固定包含：非 root user、`read-only`、有界 tmpfs、`cap-drop=ALL`、`no-new-privileges`、CPU/memory/PID 限制、network、workspace staging 单一 bind mount、固定 workdir、显式 env、`pull=never`；不得出现 privileged、host network、device、额外 volume 或 Docker socket。
4. `docker start --attach` 收集 stdout/stderr；取消/超时时先停止 attach，再按 ID stop/kill/rm，不能靠名称或模糊查询删除。
5. `docker inspect` 取得真实 exit code、OOM、image ID/digest 和状态；CLI 文本不是唯一事实源。
6. collect 在宿主比较 staging before/after manifest，不使用容器内生成的自述清单。
7. cleanup 以 execution ID/label 和已持久化 container ID 为依据，显式 remove；`--rm` 只能作为辅助，不能代替 cleanup 证据。

所有 argv builder 单独单测，拒绝换行、NUL、空 argv、绝对/越界 cwd、未允许 network、tag-only image 和任意额外挂载。错误分类至少包括：`docker_cli_missing`、`daemon_unavailable`、`unsupported_platform`、`image_missing`、`image_digest_mismatch`、`capability_missing`、`container_create_failed`、`container_start_failed`、`container_oom`、`timeout`、`cancelled`、`result_unknown`、`cleanup_failed`。

## 8. 工作区 staging 与工件回传

### 8.1 WorkspaceStager

新增 `adapters/execution/workspace.py`：

- staging 根位于 Deity 管理的临时目录，不在用户仓库内；目录名只含 execution ID。
- 复制前捕获 V0.5 `WorkspaceSnapshot`；遍历使用明确文件数/总字节/单文件上限。
- 默认不复制 `.git`、Deity DB、`.deity`、`.env*`、socket、FIFO、device、超界 symlink；配置只能追加排除项。
- 普通文件按字节复制，保留必要可执行位；不保留 owner/setuid/setgid。目录权限归一化为 staging 可用的最小权限。
- symlink 默认拒绝该 execution，而不是跟随；若未来允许内部 symlink，需另写 ADR 和完整逃逸测试。
- 复制完成后生成独立 staging baseline manifest；manifest 不含文件正文和秘密，只含相对路径、类型、size、mode、hash。
- 任何复制期间的宿主漂移都导致 `workspace_changed_during_stage`，不启动容器。

### 8.2 ArtifactCollector

执行后在宿主重新扫描 staging，与 baseline 对比：

- 仅接受工作区内普通 UTF-8/UTF-8 BOM 文本的 create/modify/delete 候选。
- 特殊文件、symlink、hardlink 异常、路径大小写碰撞、绝对/`..` 路径、超限文件、二进制和未知编码标 rejected。
- manifest 记录 before/after hash、size、mode、operation；内容作为受控临时 artifact，不直接写事件 JSON。
- Verification 永远只保留摘要/Evidence，丢弃 staging 变化。
- `artifact_policy=discard` 时不写回，但仍记录 manifest 和原因，方便诊断命令副作用。

### 8.3 ArtifactApplier

`artifact_policy=review` 时按以下顺序应用：

1. 重新捕获宿主目标 preimage，比较 Run baseline 与当前状态。
2. 复用 dirty path 精确授权、Plan target、read-before-write 和 workspace_write permission。
3. create 要求当前不存在；modify/delete 要求 hash 未漂移；symlink/submodule/conflict/.git 一律拒绝。
4. 每个文本文件使用临时文件、fsync、`os.replace`；删除只处理已验证的单个普通文件。
5. 每个成功条目在 outcome 后写 `FileChange`；失败条目标 rejected/partial，不掩盖已完成条目。
6. 崩溃发生在文件替换后、数据库 outcome 前时，ChangeSet 与 manifest 标 unknown，恢复要求人工对账，禁止自动重复应用。

V0.6 不承诺多个文件的文件系统级原子事务；因此多文件回传必须有逐文件状态和 partial/unknown 语义，最终报告明确哪些文件已应用、拒绝或待协调。

## 9. 工具与 Verification 接入

### 9.1 shell

- `LocalToolDispatcher` 保留 schema、边界、审批和工具 definitions；将 `_process` 替换为注入的 `CommandExecutionPort`。
- `RunService._compose_dispatcher()` 根据配置和 capability preflight 组合 Local 或 Docker coordinator，再叠加 Skill/Code Intelligence/Plan/Git Guard。
- Plan 模式仍在 durable intent 前拒绝 shell；Hook/MCP/AGENTS.md 不能改变 backend required 决策。
- Docker shell 的 cwd 只能是 workspace-relative，并映射到容器固定 `/workspace/...`。
- shell 的 ToolResult 来自已持久化 ExecutionResult；artifact apply 结果通过 Evidence/ChangeSet 单独展示，不能仅靠 exit 0 宣称宿主变更成功。

### 9.2 Verification

- `VerificationExecutor` 改为依赖 `CommandExecutionPort`，不再拥有 subprocess 实现。
- `ProjectVerificationDetector` 保持固定 argv 探测逻辑；Docker adapter 不接受 shell wrapper。
- `VerificationService` 先保存 plan 和 workspace snapshot，再为每个命令创建 sandbox execution；每项 Evidence 关联 `execution_id`、backend、image digest、exit code、OOM/timeout 和 cleanup status。
- Verification artifact policy 固定 discard；exit 0 但 cleanup failed、result unknown、OOM、Evidence 未提交或检查数不完整时不能聚合为 PASSED。
- Docker 不可用且 sandbox required 时检查为 `NOT_RUN` 或 `INCONCLUSIVE` 的精确语义由 ADR 冻结：预执行 capability 拒绝建议 `NOT_RUN(reason=sandbox_unavailable)`；执行开始后未知/cleanup failure 建议 `INCONCLUSIVE`。

## 10. SQLite v5 与事件协议

迁移前对 v4 数据库创建 `.v4.bak`，打开备份并确认 `MAX(schema_migrations)=4` 后才执行 v5。新增 `adapters/storage/schema_v5.py`，建议表：

```text
sandbox_executions(
  id PRIMARY KEY, run_id REFERENCES runs, call_id, backend, status,
  spec_json, capabilities_json, image_ref, image_digest, container_id,
  started_at, ended_at, exit_code, error_code, result_json,
  UNIQUE(run_id, call_id)
)

artifact_manifests(
  id PRIMARY KEY, execution_id UNIQUE REFERENCES sandbox_executions,
  status, baseline_snapshot_id REFERENCES workspace_snapshots,
  summary_json, created_at, applied_at
)

sandbox_artifacts(
  id PRIMARY KEY, manifest_id REFERENCES artifact_manifests,
  ordinal, path, operation, before_sha256, after_sha256,
  size_bytes, mode, status, file_change_id,
  UNIQUE(manifest_id, ordinal)
)

sandbox_cleanups(
  id PRIMARY KEY, execution_id UNIQUE REFERENCES sandbox_executions,
  status, container_removed, staging_removed, diagnostics_json, created_at
)
```

敏感 env value、完整 stdout/stderr、文件正文、宿主 home 和 Docker credentials 不进入表或事件。大输出进入现有有界 Evidence；事件只保存 ID、状态和摘要。

新增版本化事件：

- `SandboxExecutionPrepared`
- `SandboxBackendSelected`
- `SandboxStarted`
- `SandboxCompleted` / `SandboxOutcomeUnknown`
- `ArtifactManifestCollected`
- `ArtifactApplied` / `ArtifactApplyPartial` / `ArtifactApplyUnknown`
- `SandboxCleanupCompleted` / `SandboxCleanupFailed`
- `SandboxCapabilityRejected`

事务要求：intent 与 execution row 同事务；result 与完成事件同事务；manifest + entries 同事务；每个 artifact apply outcome 与对应 `FileChange` 同事务；cleanup row 与事件同事务。CLI 事件发布在 commit 之后。

迁移测试必须覆盖 v1/v2/v3/v4→v5、空库、重复 open、损坏 `.v4.bak`、磁盘/DDL 失败、外键、唯一约束和回滚。代码回退时保留 v5 只读，不执行删表逆迁移；需要运行旧二进制时，停止 Deity 后在隔离路径验证并恢复 `.v4.bak`。

## 11. CLI 与用户流程

新增 `interfaces/cli/sandbox.py`，`main.py` 只注册：

```text
deity sandbox doctor --config ...
deity sandbox run --workspace ... --config ... -- <argv...>
```

`doctor` 是只读诊断，不拉镜像、不构建镜像、不启动业务命令；输出：backend、平台、CLI/daemon 状态、image ref/digest、能力、默认网络、资源限制支持、staging probe、结论和失败原因。不得输出 Docker credential、env value 或完整 daemon 配置。

`run`：

- 必须在 `--` 后接受 argv，不经 shell 解析。
- 默认 artifact discard；只有配置允许且用户显式选择 apply/review 时才进入回传审批。
- 显示 backend、镜像 digest、网络、资源预算、workspace mode、execution ID、exit code、cleanup 和 artifact 摘要。
- sandbox required 但 doctor/capability 不满足时退出码非零，明确写“未执行”，不调用 Local。

普通 `deity run/build/verify/resume` 从配置选择 backend。resume 遇到 unknown execution、活动容器、cleanup 未完成、image/config 漂移时只允许 inspect/manual review；另行设计的 cleanup/reconcile 命令如确有验收需求，必须追加到 ADR，不在实现中临时加入模糊的批量删除命令。

## 12. 分阶段实施与门禁

### P0：基线、威胁模型与 ADR

**先写/更新：** ADR-012、威胁模型、依赖评审、V0.6 配置草案、当前门禁报告。

3. 冻结本文 S0 决策；任何直接可写宿主挂载、自动 pull 或 local fallback 提案必须单独评审。

**门禁：** ADR、非目标、错误分类、回退和依赖记录齐全；否则不编码。

### P3：Docker doctor、能力协商与安全 argv

**测试先行：** CLI 缺失、daemon unavailable、tag-only、digest mismatch、unsupported platform、每个必选 flag、禁止 flag/挂载、network allowlist、capability fail closed。

**实现：** Docker argv builder、doctor、selector、create/start/inspect/log/cleanup 基础生命周期。先用不会修改工作区的命令完成真实 fixture。

**门禁：** required 模式不发生 Local 调用；容器为非 root、rootfs read-only、capabilities 全 drop、no-new-privileges、无 Docker socket、默认 network none；审计得到真实 image digest/container ID。

### P4：staging、manifest 与清理

**测试先行：** 大仓库上限、并发漂移、外部 symlink、socket/FIFO、权限位、大小写冲突、容器新增/修改/删除、二进制/超限、cleanup failure 和孤儿容器。

**实现：** WorkspaceStager、host-side manifest、ArtifactCollector、cleanup report；Verification 固定 discard。

**门禁：** 宿主工作区在 collect 前字节不变；越界/特殊文件零回传；timeout/cancel 后无受控容器和 staging 残留；清理失败可查询且阻断候选。

### P5：shell/Verification 集成与工件回传

**测试先行：** Plan shell deny、shell docker route、verify pass/fail/not-run/inconclusive、dirty/plan target/preimage、partial apply、文件替换后崩溃、Evidence 缺失。

**实现：** RunService/LocalToolDispatcher/VerificationService 注入统一端口；ArtifactApplier 复用 Git Guard/ChangeSet；CLI sandbox run。

**门禁：** Docker shell 不直接写宿主；Verification 生成物不回传；artifact review 仍需现有授权；unknown/partial 不标 completed/PASSED。

### P6：资源、网络、秘密与恢复故障注入

**测试先行：** 内存超限/OOM、PID 爆炸、CPU/timeout、输出洪泛、取消、named network 拒绝、宿主 secret 哨兵、socket 探测、daemon 重启、CLI attach 中断、outcome 前后崩溃。

**实现：** 完整错误映射、inspect 协调、resume manual-review 判定、事件和 Evidence 字段。

**门禁：** secret/socket 不可见；资源超限有明确状态；无自动重放；每个 execution 最终有 result/unknown 与 cleanup/failed 事实。

### P7：评估、文档、候选验收与回退演练

**实现：** S01–S12、runner、fixture Dockerfile、CI 分层、使用说明、README/开发/评估更新、候选报告。

**门禁：** ruff/format/mypy/pytest、E/R/X/A/S 全过；Linux Docker 集成全过；macOS 非 Docker 回归全过；`.v4.bak` 恢复演练成功；任何真实 Docker/远程 CI/真实模型未运行项明确记录。

## 14. 测试与故障注入矩阵

### L0 单元/协议

- `deity sandbox doctor/run` 安装后 CLI。

- sandbox unavailable 的 `deity run/build/verify/resume` 全部 fail closed。

每阶段执行：先补失败测试 → 最小实现 → focused 回归 → 故障注入 → 旧门禁 → 文档/回退 → 中文提交。未通过本阶段门禁不得提前启用下一阶段功能。

## 18. 风险、监控与回退

| 风险 | 预防 | 触发后处理 |
|---|---|---|
| 容器逃逸/daemon 高权限 | 最小挂载、非 root、cap drop、no-new-privileges、无 socket、及时更新 | 立即关闭 sandbox，阻断发布，保留审计并升级依赖 |
| 镜像供应链 | digest pin、pull never、CI 本地 fixture、记录真实 image ID | 拒绝运行，替换并重新验收镜像 |
| 网络泄漏 | 默认 none、显式 network allowlist/审批 | 禁用非 none 网络，报告安全事件 |
| 宿主秘密泄漏 | env 默认空、staging exclude、无 home/socket、日志脱敏 | 停止 Run、轮换相关秘密、阻断候选 |
| 用户改动覆盖 | staging、manifest、dirty/preimage/Plan target、原子写 | 标 partial/unknown，人工对账，不重放 |
| 资源耗尽 | CPU/memory/PID/tmpfs/timeout/output 上限 | kill/remove，记录 OOM/limit，调整 fixture 后重测 |
| 清理失败/孤儿容器 | stable ID/label、finally cleanup、重启协调 | 标 cleanup_failed，禁止 PASS，精确 ID 人工清理 |
| macOS/Windows 差异 | capability doctor、Linux 阻断、macOS 手工记录、Windows fail closed | 不降级 Local；标 NOT_SUPPORTED/NOT_RUN |
| SQLite 迁移失败 | `.v4.bak`、单事务、打开验证 | 原库不变；隔离验证备份后恢复 |
| 性能不可接受 | staging 冷/热基线、文件/字节上限、指标 | 关闭 sandbox 或缩小范围；不改为直接可写挂载 |

功能回退顺序：

1. 设置 `[sandbox].enabled=false`，确认 shell/Verification 回到 V0.5 Local 路径。
2. 停止新的 sandbox execution；按精确 execution ID 协调已记录的活动/unknown 容器和 staging，禁止全局批量清理。
3. 保留 SQLite v5 facts 只读，运行 V0.5 E/R/X/A 和旧 CLI 回归。
4. 如必须运行旧二进制，停止 Deity，备份 v5，再在隔离路径打开验证 `.v4.bak` 后恢复；不做逆向删表。
5. 回退后报告哪些 execution/artifact/cleanup 仍为 UNKNOWN，不把“开关关闭”描述为问题已解决。

## 19. 最终 Definition of Done

- ADR-012 已采纳，威胁模型、Docker CLI、staging、网络、镜像、恢复和依赖决策明确。
- Core 通过 Protocol 支持 Local/Fake/Docker，Docker 细节不进入 Core/Application/CLI。
- sandbox 默认关闭；开启且 required 时，Docker/能力不可用会 fail closed，绝不静默 Local fallback。
- Docker 使用 digest pin、非 root、read-only rootfs、cap drop、no-new-privileges、默认禁网、CPU/memory/PID/tmpfs/timeout/output 限制和最小 staging mount。
- 宿主 secrets、Docker socket、home、Deity DB 不暴露；日志、事件、数据库无敏感值。
- shell 与 Verification 使用统一后端；Verification 四状态仍来自已提交真实 Evidence。
- staging/manifest/artifact apply 经过路径、symlink、size、encoding、dirty、preimage、Plan target、权限和 ChangeSet 检查。
- timeout/cancel/crash/daemon failure 都有 typed result、unknown 协调和 cleanup 证据；无自动重放。
- SQLite v5 迁移、`.v4.bak` 验证和恢复演练通过；旧事实只读兼容。
- ruff、format、mypy、pytest、E01–E08、R01–R06、X01–X06、A01–A12、S01–S12 通过；Linux Docker job 通过。
- README、开发指南、评估计划、V0.6 使用说明、候选报告和回退步骤齐全。
- 真实模型、远程 CI、macOS Docker、Windows 等任何未运行/不支持项明确标 `NOT_RUN/NOT_SUPPORTED/UNKNOWN`；未满足以上条件不得声明 V0.6 候选通过。
