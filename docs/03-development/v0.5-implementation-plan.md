# Deity V0.5 Advanced Coding Agent 实施计划

> 状态：本地候选实现已完成。需求依据：[V0.5 设计](../05-roadmap/deity-v0.5-design.md)。运行基线由 V0.4、SQLite v3 升级至 SQLite v4；本地验证结果、未运行项与风险见 [V0.5 候选验收记录](../04-evaluation/v0.5-candidate-2026-11-01.md)。

## 1. 目标、范围与完成定义

V0.5 把现有“模型调用基础工具”的闭环升级为可计划、可定位、保护用户改动并用真实证据交付的 Coding 工作流。交付包含四项能力：

1. `deity plan` 生成结构化、只读、可持久化的计划；`deity build --plan <id>` 显式批准计划并创建新的 Build Run。
2. 面向 Python、Java、TypeScript 的符号定义与文本引用定位，结果携带来源和置信级别，并支持有界缓存失效。
3. 写入前捕获 Git/工作区基线，保护用户已有改动，生成 Agent ChangeSet，并安全处理补丁冲突、CRLF、symlink、submodule 和非 Git 工作区。
4. `deity verify` 确定性探测并执行 compile/test/lint，产出 `PASSED/FAILED/NOT_RUN/INCONCLUSIVE` 和可追溯 Evidence。

V0.5 完成必须同时满足：契约、实现、正常/异常/取消测试、安全回归、A01–A12 评估、迁移/恢复演练、CLI 演示、文档和回退方案全部交付。任何未运行项目标记 `NOT_RUN`，不得用模型文字替代执行证据。

### 1.1 明确不做

- 不引入 LangChain、LangGraph、Deep Agents Runtime、FastAPI、TUI、Multi-Agent、Docker、RAG 或自动模型切换。
- 不实现完整 IDE 级语义数据库、后台常驻 LSP、自动 Git commit、自动 stash、自动 reset/clean 或远程 Git 操作。
- 不把 worktree 隔离作为 V0.5 必选运行路径；只允许在 S6 的可丢弃 fixture 中做限时试验，试验失败不得削弱基线 Git Guard。
- 不在首个切片同时引入 tree-sitter 与 LSP。强制验收先用标准库、`rg` 和 Git CLI；只有精度基线不达标时才单独提交依赖 ADR。
- 不让 Plan 文本、Skill、MCP 输出、仓库指令或模型自述提升权限。
- 不把本地路径和 Git 保护描述为操作系统沙箱。

## 2. 当前基线与实施原则

当前 `AgentRequest`、`RunService`、`LocalToolDispatcher` 和 `SQLiteSessionRepository` 已承担大量职责；SQLite 为 v3，CI 为 Ubuntu/macOS × Python 3.12/3.13，确定性评估为 E01–E08、R01–R06、X01–X06。V0.5 采用增量模块，不重写 Agent Loop，不破坏现有工具名、旧 Run、旧事件和禁用新功能后的 V0.4 路径。

固定依赖方向：

```text
CLI commands
  → PlanService / BuildService / CodeIntelligenceService / VerificationService
    → Core DTO / Protocol / Policy
      ← adapters/code_intelligence
      ← adapters/git
      ← adapters/verification
      ← adapters/storage v4
```

Core 不导入 Typer/Rich、SQLite、Git 子进程、厂商 SDK 或解析器 SDK。所有工作区副作用继续经过 schema → mode policy → boundary → permission → durable intent → execution → durable outcome/audit。

## 3. S0：先决 ADR 与冻结决策

编码前新增 `docs/02-architecture/adr-011-v0.5-advanced-coding.md`，冻结以下内容：

| 决策 | V0.5 选择 | 兼容/风险处理 |
|---|---|---|
| Plan 权限 | Tool Runtime 强制只读；允许读取、Glob、grep、Git status/diff、Code Intelligence、Skill 读取和 `submit_plan`；拒绝写/删、Shell 和未知效果 MCP | 不依赖提示词；拒绝事件可审计 |
| Plan→Build | `build --plan` 本身是显式批准；校验计划 hash、TTL、需求 hash 和工作区快照后创建新 Run | 不原地提升 Plan Run 权限 |
| 计划结构 | 模型提交 `PlanDraft`；系统生成 ID、hash、状态、时间和来源形成 `PlanArtifact` | 严格 Schema，拒绝部分/额外字段 |
| Code Intelligence | 必选 lexical backend：标准库 + `rg`；结果标 `definition/textual_reference` 和 `lexical` 来源 | 不伪装为精确语义引用 |
| 缓存 | XDG cache 下独立索引 SQLite/JSON；不写用户工作区 | key 含 workspace identity、相对路径、mtime、size、hash、backend version |
| Git 保护 | 启动 Build 时记录 HEAD、porcelain v2 状态、submodule 和目标文件基线；默认拒绝改动初始 dirty path | 可通过显式 `--allow-dirty <path>` 逐路径授权 |
| Patch | UTF-8/UTF-8 BOM、有界文本、原换行风格、精确上下文、原子替换 | 冲突不覆盖，二进制/编码未知拒绝 |
| Verification | 探测器生成固定命令，执行器独立于模型自由 Shell；默认权限 `ask`，可配置 `auto/deny` | 每项有 timeout、输出上限、取消和 Evidence |
| 存储 | SQLite v3→v4 正向迁移；迁移前生成并验证 `.v3.bak` | 旧事件只读，关闭开关后 V0.4 可运行 |

ADR 同时记录：V0.5 必选实现不新增运行时依赖；tree-sitter/LSP 只有在三语言 fixture 的 lexical 精度不能满足已定义验收时才评审，届时补用途、许可证、版本、维护、安全、替代方案和移除成本。

S0 还要记录当前主干基线命令和真实结果。历史 V0.4 报告只作参照，不作为 V0.5 PASS。

## 4. 共享契约与不变量

### 4.1 Core DTO

在 `src/deity/core/contracts/` 增加模块并从 `__init__.py` 重导出：

```python
class ExecutionMode(StrEnum):
    PLAN = "plan"
    BUILD = "build"
    VERIFY = "verify"

@dataclass(frozen=True)
class PlanStep:
    ordinal: int
    title: str
    description: str
    files: tuple[str, ...]
    verification: tuple[str, ...]

@dataclass(frozen=True)
class PlanDraft:
    schema_version: int
    goal: str
    assumptions: tuple[str, ...]
    steps: tuple[PlanStep, ...]
    risks: tuple[str, ...]
    verification: tuple[str, ...]

@dataclass(frozen=True)
class PlanArtifact:
    plan_id: str
    source_run_id: str
    session_id: str
    draft: PlanDraft
    sha256: str
    requirements_sha256: str
    workspace_snapshot_id: str
    status: Literal["draft", "approved", "stale", "rejected"]
    created_at: str

@dataclass(frozen=True)
class SymbolLocation:
    path: str
    line: int
    column: int | None
    symbol: str
    language: Literal["python", "java", "typescript", "unknown"]
    kind: str
    source: Literal["lexical", "tree_sitter", "lsp"]
    confidence: Literal["exact_definition", "candidate_definition", "textual_reference"]

class PatchApplyStatus(StrEnum):
    APPLIED = "applied"
    CONFLICT = "conflict"
    DENIED = "denied"
    UNKNOWN = "unknown"

@dataclass(frozen=True)
class PatchApplyResult:
    status: PatchApplyStatus
    path: str
    before_sha256: str | None
    after_sha256: str | None
    evidence_id: str | None
    error_code: str | None

class VerificationStatus(StrEnum):
    PASSED = "passed"
    FAILED = "failed"
    NOT_RUN = "not_run"
    INCONCLUSIVE = "inconclusive"
```

另定义 `PlanApproval`、`ReferenceQuery`、`WorkspaceFileState`、`WorkspaceSnapshot`、`GitCheckpoint`、`FileChange`、`ChangeSet`、`VerificationCommand`、`VerificationPlan`、`VerificationEvidence`、`FinalReport`。`GitCheckpoint` 只引用工作区快照、ChangeSet 与 Evidence，不代表或创建 Git commit。所有 DTO 使用不可变类型、长度/数量上限和稳定 canonical JSON；hash 不包含密钥、绝对 home 路径或非确定时间字段。`requirements_sha256` 只根据 Unicode 规范化后的原始用户任务和显式约束计算，不包含模型生成的计划文本。

`AgentRequest` 新增 `execution_mode=BUILD`、`plan_id=None`、`policy_fingerprint=""`。这些字段进入 `config_fingerprint()`；旧 Run 缺失 mode 时按 `build` 读取。Run 状态机不新增 Plan 终态，计划状态独立持久化。

### 4.2 Core Protocol

- `ExecutionPolicy.authorize(tool_name, arguments, mode) -> PolicyDecision`
- `PlanRepository.create/get/approve/mark_stale/link_build`
- `CodeSearchPort.find_symbol/find_references/index_status`
- `IndexCache.get/put/invalidate`
- `WorkspaceSnapshotPort.capture/compare`
- `ChangeSetRepository.start/record/finalize`
- `Verifier.detect/run`
- `VerificationRepository.create_plan/record_check/complete`

协议只描述数据和行为，不出现 `subprocess`、SQLite row、Typer 或具体解析器类型。

### 4.3 Runtime 不变量

1. Plan Run 的任何写工具、删除、Shell、MCP 业务工具都在 durable intent 前拒绝；`submit_plan` 只写 Deity 状态库，不写工作区。
2. 一个 PlanArtifact 只能批准一次；批准与 Build Run 创建在同一 SQLite 事务完成。失败不得留下“已批准但无 Build Run”。
3. Build Run 必须引用批准时的 plan hash；计划过期、工作区漂移或需求 hash 不一致时拒绝创建。
4. 每个 Build Run 只有一个活动 ChangeSet；每条 `call_id` 仍唯一，用户初始改动不得被静默覆盖。
5. Verification 的完成状态必须由已提交检查结果聚合；无检查不能是 PASSED。
6. 结果未知的写入、Git 动作或验证子进程不得自动重放。

## 5. 配置与功能开关

新增严格版本化配置，默认全部关闭，避免升级后改变旧行为：

```toml
[coding]
version = 1
plan_build_enabled = false
code_intelligence_enabled = false
git_guard_enabled = false
verification_enabled = false
plan_ttl_seconds = 86400

[code_intelligence]
backend = "lexical"
cache_enabled = true
max_files = 20000
max_file_bytes = 2000000

[git_guard]
protect_initial_dirty = true
require_read_before_write = true

[verification]
permission = "ask"  # ask | auto | deny
timeout_seconds = 300
max_output_chars = 16000
repeat = 1
```

配置解析继续拒绝未知字段。范围建议：TTL 300–604800 秒；索引文件数 1–100000；单文件 1 KiB–8 MiB；验证超时 1–1800 秒；repeat 1–3。`coding`、索引 backend/version、Git policy 和 Verification policy 进入恢复指纹。功能开关关闭时不注册新工具、不创建新缓存、不改变旧 Run 行为。

## 6. SQLite v4 与事件协议

迁移前对 v3 数据库创建 `.v3.bak`，打开备份并确认 `MAX(schema_migrations)=3` 后才执行 v4。建议新增：

```text
workspace_snapshots(id, workspace_root, git_head, status_json, digest,
                    backend_version, created_at)
plans(id, source_run_id, session_id, status, schema_version, artifact_json,
      sha256, requirements_sha256, workspace_snapshot_id, created_at, approved_at)
plan_builds(plan_id PRIMARY KEY, build_run_id UNIQUE, approval_json, created_at)
change_sets(id, run_id UNIQUE, baseline_snapshot_id, status, summary_json,
            created_at, completed_at)
file_changes(id, change_set_id, ordinal, path, operation, before_sha256,
             after_sha256, source_call_id, status, UNIQUE(change_set_id, ordinal))
verification_runs(id, run_id, workspace_snapshot_id, status, plan_json,
                  started_at, ended_at)
verification_checks(id, verification_id, ordinal, kind, argv_json, status,
                    exit_code, evidence_id, duration_ms, UNIQUE(verification_id, ordinal))
```

外键均启用；hash、状态和 JSON 长度在写入前校验。`plan_builds` 独立于现有 resume `run_lineage`，不改变“一次恢复一个 successor”的约束。索引缓存不进入主审计库，避免大规模符号记录拖慢 Run 事务。

新增版本化事件：`WorkspaceSnapshotCaptured`、`PlanSubmitted`、`PlanApproved`、`PlanMarkedStale`、`BuildRunLinked`、`ChangeSetStarted`、`FileChangeRecorded`、`ChangeSetFinalized`、`CodeIndexUpdated`、`VerificationPlanned`、`VerificationCheckCompleted`、`VerificationCompleted`。事件只保存摘要和 ID；大输出进入有界 Evidence，不复制到事件。

## 7. 分阶段实施

### S1：共享基础、配置和 SQLite v4

**目标：**先落地 DTO/Protocol、策略接口、配置开关和可回滚存储，不开放用户功能。

**主要文件：**

- 新增 `core/contracts/{planning,code_intelligence,workspace,verification}.py`、`core/policy.py`。
- 修改 `core/contracts/__init__.py`、`application/config.py`、`core/storage.py`。
- 新增 `adapters/storage/schema_v4.py`，在 `adapters/storage/__init__.py` 接入迁移和仓库方法。
- 新增 ADR、迁移 fixture 和配置/存储测试。

**顺序：**先写旧 v3 fixture 可读和备份失败测试；再写 DTO/配置失败测试；然后实现迁移；最后验证所有开关关闭时请求指纹和工具列表与 V0.4 一致。

**门禁：**迁移事务失败时原库不变；备份验证失败时拒绝迁移；v1/v2/v3 逐级升级可读；未知配置 fail closed；E/R/X 全部通过。回退方式是关闭开关并使用经验证的 `.v3.bak` 在隔离路径读取，不做删表式逆迁移。

### S2：Plan/Build 双模式

**目标：**实现只读计划、结构化提交、显式批准和新 Build Run。

**实现步骤：**

1. `ExecutionPolicy` 根据 mode 过滤工具。PLAN 只允许 `read_file/list_files/glob/grep/git_status/git_diff/find_symbol/find_references/load_skill/load_skill_resource/submit_plan`；Shell、写/删和 MCP 业务工具直接返回 `mode_policy_denied`。
2. 新增 `PlanningDispatcher` 包装现有 dispatcher，暴露严格 `submit_plan` Schema。模型提交 `PlanDraft` 后，系统计算 requirements hash、计划 hash 和 workspace snapshot，并在工具 outcome 提交前后按现有 intent/outcome 规则持久化 PlanArtifact。
3. 新增 `PlanService.create/list/show`。Plan Run 可继续让模型输出简短摘要，但正式事实来自 PlanArtifact；没有成功 `submit_plan` 的 Run 不得显示为“计划已生成”。
4. 新增 `BuildService.start(plan_id, allow_dirty_paths)`：事务内检查功能开关、状态、TTL、hash、workspace、snapshot 和已有 Build；记录 PlanApproved 并创建 `execution_mode=build` 的新 Run。
5. CLI 增加 `deity plan <task>`、`deity plans list/show <id>`、`deity build --plan <id> [--allow-dirty PATH]`。`build` 命令本身即明确批准，不再弹第二个模糊确认框。
6. 用户在计划后改变需求时创建新 Plan；不得在 `build` 中附加新任务文本。旧计划因 TTL 或工作区漂移标记 stale。

**失败路径：**模型提交额外字段/超限步骤/重复 ordinal；尝试 Shell 或写工具；进程在 PlanSubmitted 前后崩溃；重复 build；审批事务失败；计划过期；计划文件涉及初始 dirty path；取消时未完成 Plan 不产生可用 artifact。

**门禁：**fixture 中所有写操作和可变 Shell 100% 被阻断；Plan→Build 关系唯一；Plan hash/需求 hash/快照任一漂移均拒绝；V0.4 `deity run` 行为不变。功能开关保持关闭，直到 S4 Git Guard 完成。

### S3：Code Intelligence

**目标：**提供三语言、有来源标记、可复核的符号候选和文本引用。

**实现步骤：**

1. 新增 `adapters/code_intelligence/lexical.py`：按后缀识别 Python/Java/TS，使用有界逐行扫描和 `rg`。Python 识别 class/def/async def；Java 识别 class/interface/enum/record 及保守方法候选；TS 识别 class/interface/type/function/enum 和变量声明候选。
2. `find_symbol(name, language?, path?)` 返回定义候选；`find_references` 用标识符边界查找文本引用。重名全部返回，不由 Adapter 猜唯一答案。
3. 结果包含相对路径、1-based 行号、kind、source 和 confidence；模型必须再 `read_file` 复核上下文。二进制、过大文件、未知编码跳过并返回 diagnostics。
4. 新增 XDG cache adapter。缓存键为 workspace identity + backend version；文件 entry 含相对路径、size、mtime_ns、sha256。Git HEAD 变化不直接使全部缓存失效，逐文件 key 决定复用；删除/重命名清理旧 entry。
5. Application 增加 `CodeIntelligenceService`；工具层增加 `find_symbol/find_references`；CLI 增加 `deity code symbol NAME`、`deity code references NAME` 供独立诊断。

**大型仓库边界：**默认最多 20,000 文件、单文件 2 MiB、输出 200 条；超限返回 `partial=true` 和 diagnostics，不能静默当完整结果。submodule 默认仅作为边界节点，不递归索引。

**依赖决策门：**若 A04–A06 无法在固定 fixture 达到“定义 100% 命中、结果行号正确、重名不丢失”，先修正 lexical 规则；仍不能满足才提交 tree-sitter 或 LSP ADR。不得为追求“语义”名称提前装完整栈。

### S4：Git 与补丁安全

**目标：**在开放 Build 前保护用户已有改动并形成可核验 ChangeSet。

**实现步骤：**

1. `GitWorkspaceAdapter.capture()` 使用 `git rev-parse`、`git status --porcelain=v2 -z`、submodule 状态建立基线；非 Git 工作区返回 `git_head=None`，继续使用文件 preimage 保护。
2. Build 启动时创建 WorkspaceSnapshot 和 ChangeSet。记录初始 modified/staged/untracked/conflicted 路径，不执行 stash/commit/reset/clean。
3. 对 `read_file` 记录 path + sha256 作为 preimage。`apply_patch/delete_file` 默认要求目标已读且当前 hash 未变化；`write_file` 要求路径在基线和当前均不存在。
4. 初始 dirty path 默认拒绝写入；只有 `build --allow-dirty path` 精确列出的相对普通文件可修改，授权进入审批事实和恢复指纹。目录、glob、绝对路径和 symlink 不接受授权。
5. 新增 `SafePatchApplier`：检测 UTF-8/BOM、换行风格和二进制 NUL；要求 old context 唯一；写临时文件并 fsync 后 `os.replace`；替换前再次校验 preimage。冲突返回 `patch_conflict`，不产生部分写入。
6. 每次成功写/删在 outcome 持久化后记录 `FileChange`；Run 终态生成 ChangeSet 摘要、`git diff --no-ext-diff` 证据和用户原改动保持检查。Checkpoint 不创建 Git commit。

**边界处理：**CRLF 保持原风格；symlink 和 `.git` 拒绝；submodule 内写入默认拒绝；merge conflict 路径拒绝；无 Git 仓库仍支持新文件和已读普通文件的受保护修改；用户并发修改触发 preimage mismatch。

**门禁：**用户初始改动字节级保持；冲突时零覆盖；Agent ChangeSet 只包含本 Run 成功 outcome；崩溃后 unknown 写入不自动重放。完成后才允许 `plan_build_enabled=true` 用于候选验收。

### S5：Verification Engine 与 FinalReport

**目标：**用确定性执行证据形成交付结论。

**探测器：**

- Python：读取 `pyproject.toml` 和锁文件，按实际配置选择 `uv run --locked pytest -q`、`ruff check .`、`ruff format --check .`、`mypy src`；缺少对应配置/依赖时不臆造命令。
- Java：优先仓库内 `./mvnw test` 或 `./gradlew test`，其次在配置允许时使用 `mvn test`；不下载 wrapper、不改全局环境。
- TypeScript：只使用 `package.json` 中明确存在的 `test/lint/typecheck/build` script 和已存在的 lockfile/package manager；不自动安装依赖。
- 用户可在配置中添加 argv 数组白名单，禁止 shell 字符串、管道和 `sh -c`。

`Verifier` 先输出可展示的 VerificationPlan，再根据 `ask/auto/deny` 决策执行。每项使用受限 cwd、环境白名单、timeout、输出上限和取消清理；开始前记录 intent，结束后记录 exit code、duration、输出摘要和 Evidence ID。

聚合规则：至少一个必需检查运行且全部成功为 PASSED；任何必需检查正常启动后非零为 FAILED；权限拒绝或未发现检查为 NOT_RUN；缺依赖、超时、取消、输出不可判定或 repeat 结果不一致为 INCONCLUSIVE。默认不自动重试；`repeat>1` 是显式配置，结果不一致标 flaky/INCONCLUSIVE。

新增 `VerificationService.detect/run/report` 和 `deity verify [--run RUN_ID] [--show-plan]`。Build 完成时若开关启用，可调用同一 Service；模型不能把未执行命令写成 PASS。FinalReport 至少包含结论、ChangeSet、检查状态、Evidence ID、失败/未运行原因和剩余风险。

**门禁：**预置失败测试不得报 PASSED；无测试项目不得报 PASSED；缺依赖不伪装代码失败；取消清理子进程；Evidence 与实际退出码一致。

## 12. 风险、监控与回退

| 风险 | 预防 | 触发后的处理 |
|---|---|---|
| Plan 只读绕过 | mode policy 在 Tool Runtime、未知工具拒绝 | 关闭 plan_build 开关，阻断发布 |
| 用户改动覆盖 | dirty 基线、read-before-write、preimage、原子 patch | 停止 Run，保留 ChangeSet 和 unknown，人工协调 |
| lexical 误报 | source/confidence、返回全部重名、强制 read 复核 | 调整规则；必要时走解析依赖 ADR |
| 缓存过期 | 内容 key/backend version/删除清理 | 禁用 cache，直接扫描 |
| 验证命令有副作用 | 固定 argv、权限、隔离 fixture、超时 | verification=deny，报告 NOT_RUN |
| SQLite 迁移失败 | `.v3.bak`、单事务、打开验证 | 保留原库，隔离验证备份后切回旧版本 |
| 事件/报告夸大事实 | 状态由 committed Evidence 聚合 | 候选发布阻断，修复并重跑全部门禁 |

功能级回退顺序：先关闭 `verification_enabled`、`git_guard_enabled`、`code_intelligence_enabled`、`plan_build_enabled`；保留 v4 数据和事件只读，验证 V0.4 `run/resume/mcp/skills/hooks`。代码回退不执行逆向删表。严重权限绕过、用户改动覆盖、重复未知副作用或秘密泄漏立即阻断发布。
